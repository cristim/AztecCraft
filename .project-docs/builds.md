# Build checks and packaging

The user authorized publishing the current early prototype to main. This supersedes the previous requirement to stay local until 80–90% of all Maya 2026 functionality was verified. Maya functionality coverage remains unmeasured, and publication does not establish visual or functional parity.

## Checks

`.github/workflows/check.yml` runs format, Clippy, tests and a locked release build on Ubuntu 24.04, Windows Server 2025 and macOS 15. Default desktop features remain enabled for these checks, including the native UI tests. It uses Rust 1.99.0, matching `rust-toolchain.toml`; update both pins together. Cargo commands run directly so Windows does not require Make. Jobs have timeouts, read-only repository permission and no persisted checkout credentials. Superseded pull-request runs cancel; push runs finish. No build cache is configured.

The same matrix separately runs strict Clippy for production `mcp` and `mcp-test-client`, tests with `--features mcp-test-client`, and builds production `mcp`. Explicit client-test selection includes the official SDK protocol tests rather than silently excluding them. These tests drive the real Editor with egui and do not open an OS window. Native MCP launch and client/window interaction still require a graphical session and separate verification. Default release packaging remains the ordinary desktop build. [MCP instructions](mcp.md) describe the opt-in artifact and contract.

Linux installs pkg-config, Wayland and xkbcommon development packages for the selected eframe X11/Wayland backends. These also support RFD's default portal/Wayland backend when the file-dialog slice integrates it. No GTK backend is selected, so no GTK headers are installed. A compiled Linux binary still needs a compatible graphical session, system libraries and GPU driver at runtime; build success does not establish that every distribution can launch it.

The separate Ubuntu audit job installs [cargo-audit 0.22.0](https://github.com/RustSec/rustsec/tree/cargo-audit/v0.22.0/cargo-audit) with its published lockfile and checks `Cargo.lock` against the live RustSec advisory database. Warnings fail the job. An audit needs network access and does not establish application correctness or absence of every vulnerability.

Linux also installs [cargo-llvm-cov 0.9.1](https://github.com/taiki-e/cargo-llvm-cov/tree/v0.9.1) and Rust 1.99.0's `llvm-tools-preview`, then measures headless library line coverage using `--no-default-features`, the locked workspace and all test targets. This feature selection excludes the desktop target and UI modules while retaining scene, history, document and camera workflow tests. The job fails below 80%; test-source lines are excluded from the measured denominator. This code metric measures exercised lines, not workflow correctness, native UI interactions or Maya functionality coverage. Stable line coverage does not measure every branch; critical mutation behavior still needs explicit workflow assertions.

Dependabot prepares weekly Cargo and GitHub Actions updates after an authorized repository exists. It does not merge them. Review updates and rerun checks before accepting them.

## Local pre-commit checks

With Rust 1.99.0, Python, Go and pre-commit installed, run `pre-commit install`, then `pre-commit run --all-files`. Use rustup's Cargo shim so `rust-toolchain.toml` selects the toolchain, or ensure `cargo --version` reports 1.99.0 when using a standalone Cargo installation. Hooks check whitespace, YAML, TOML and private keys. Direct Cargo hooks always check Rust formatting, Clippy, tests and the build, including commits that change only configuration. The pinned Gitleaks hook builds through pre-commit's Go environment and scans staged changes with redacted output. It requires network access on first setup. To scan existing history separately, run `gitleaks git --redact` using Gitleaks 8.30.0.

## Desktop build artifacts

The current default build produces the `azteccraft` desktop binary. After the platform's checks and release build, CI packages that exact binary and uploads its archive and SHA-256 receipt as a seven-day build artifact. These are development builds, with no release creation, deployment, notarization or signing credentials. The macOS bundle is ad-hoc signed (identity `-`) for integrity only, not with a Developer ID. Windows and Linux builds are unsigned. The separate `build-arm64` job builds, packages and smoke-runs the Linux (`ubuntu-24.04-arm`) and Windows (`windows-11-arm`) arm64 binaries natively; it runs no tests, which stay on the `check` matrix. A separate `macos-x86_64` job cross-compiles the Intel macOS build on the arm64 runner and checks its architecture and mode without launching it.

`packaging/package.py` uses only Python 3.11+ standard libraries. Supply an existing binary, `Cargo.toml` and a new output directory whose parent exists. For example, after `cargo build --release --locked`, run `python3 packaging/package.py --binary target/release/azteccraft --output target/packages --platform macos`. Use `windows` with `azteccraft.exe`, or `linux` with `azteccraft`. The script never builds or launches the input. It rejects wrong-platform formats, unsupported architectures, symlink inputs, invalid versions and occupied outputs. A failure during packaging retains its new partial output for inspection; choose another new directory on retry.

macOS receives `AztecCraft.app` with `Contents/Info.plist` and the executable under `Contents/MacOS`, inside a ZIP that preserves executable permissions. Before zipping, `package.py` runs `codesign --force --sign -` on the finished bundle and then `codesign --verify --strict --verbose=2`; packaging fails if either command fails. The linker's own ad-hoc signature covers only the executable, so without this step macOS rejects the bundle as damaged. This is integrity signing only and requires `codesign`, so macOS packages must be built on macOS. The bundle is for the input's single architecture, not a universal binary. Windows receives a ZIP containing the real `.exe`; Linux receives a tar.gz with executable permissions and neutral archive ownership. `manifest.json` records the package version, platform, detected binary architecture and binary/archive hashes. No private source paths enter this receipt. Default fonts are embedded by eframe. Icons are original vector shapes drawn in code; no image asset, reference asset or external resource is bundled.

`packaging/smoke_check.py` runs after packaging on every OS: it extracts the archive, checks the executable bit recorded in the archive, checks the binary's architecture and, for natively built binaries, runs it with an unknown argument, which prints usage and exits 2 before any window opens. It is not a graphical launch test.

Packaging checks cover fixture byte preservation, metadata, archive layout, executable modes and no-clobber failures. Fixtures test packaging behavior and do not prove that a native binary launches. Verify the actual package through the native create/edit/save/open workflow on each platform before claiming it usable there. Hosted Windows/Linux builds and graphical launch remain unverified locally; distribution installers and signed releases are future work.

Python check-tool versions are pinned in `packaging/pyproject.toml`. CI uses Python 3.13 and pip 26.2.1 to install its development group, then runs Ruff, strict mypy and pytest. Locally, create and activate a virtual environment, run `python -m pip install pip==26.2.1`, then `python -m pip install --group packaging/pyproject.toml:dev`. The same checks run through pre-commit when packaging files change. These tools are for packaging development; the packaging runtime has no third-party dependency.
